# Marmotte — AI Assistant Guide

Marmotte is an **extensible development toolkit for TypeScript projects**, organised as a **pnpm-workspace monorepo** driven by the Vite+ toolchain (`vp`). It ships composable Vite plugins (library bundling, Vue/Vuetify UI, VitePress docs, TypeDoc API generation), Vitest helpers, shared tsconfigs, and a CLI + MCP server. The monorepo is also the home for the author's day-to-day tooling (AI tools, setups documented on the docs site).

## Repository layout

```
package.json         # private root: vite-plus, devEngines (pnpm), scripts
pnpm-workspace.yaml  # workspace globs, dependency overrides (Vite+ core, vitest), allowed build scripts
vite.config.ts       # root: staged hooks, docs tasks (api-docs, docs, build:docs)
tooling/
  pack.ts            # packageConfig(): shared `vp pack` baseline + build/test tasks for a package
  copy-api-docs.ts   # interim: copies packages/*/docs/api into docs/reference/api/<package> for the VitePress site
packages/
  tsconfig/   @mrmt/tsconfig  # tsconfig bases (JSON only, no build)
  utils/      @mrmt/utils     # PRIVATE internal helpers (fs, merge, codegen, package-json schema, resolvePackageMeta): inlined, never published
  vitest/     @mrmt/vitest    # withTmpDir(), createTmpDir()
  vite/       @mrmt/vite      # Lib, Docs, dts, externals, PackageMeta, VitePluginContext
  unplugin-typedoc/             @mrmt/unplugin-typedoc              # TypeDocPlugin(), bootstrapTypeDoc()
  vitepress-plugin-sidebar/ @mrmt/vitepress-plugin-sidebar  # sidebar plugin + indent.css
  vite-ui/    @mrmt/vite-ui   # UILib / UIApp / UICommon (Vue + Vuetify)
  cli/        marmotte        # CLI + MCP server (bins: marmotte, marmotte-mcp) + scaffold tests
docs/                # VitePress site (NOT a workspace package; built from the root)
.vite-hooks/         # git hooks (pre-commit runs `vp staged`)
```

Dependency graph: `utils` (private, inlined as a devDependency of the others) → `unplugin-typedoc` → `vite` → `vite-ui`; `utils` → `vitepress-plugin-sidebar`, `cli`; `vitest` and `tsconfig` stand alone. `vitepress-plugin-sidebar` is not used by `vite`: it's only named in files generated by `Docs`, so the scaffold templates list it.

## Key patterns and conventions

### Plugin composition

Plugins are ordinary arrays of Vite `Plugin` objects. Higher-level plugins (`Lib`, `UILib`) delegate to lower-level ones and accept their options as pass-through:

```ts
// Lib() = BaseBundle() + dts() + nodeExternals() + Docs() + LibConfig()
export function Lib(options: LibPluginOptions = {}) { … }
```

### VitePluginContext — path resolution

All plugins that need filesystem paths use `VitePluginContext` (or the pre-configured `DefaultVitePluginContext`). It provides typed, root-relative path resolution:

```ts
const ctx = new DefaultVitePluginContext({ root: cfg.root });
ctx.resolve("sourceDir", "index.ts"); // → /abs/path/src/index.ts
```

`DefaultVitePluginContext` maps `sourceDir → src/`. Use `contextFactory()` to create contexts with custom named paths and typed plugin options.

`contextFactory` takes two arguments:

1. **Options object** — plugin config with defaults (empty `{}` if none). Keys become non-optional on `ctx.options`.
2. **Factory config** — `{ paths: { ... } }`. Path values can be a string (relative to `root`) or a tuple `["baseName", "relative"]` (relative to another named path).

Option keys and path keys must not overlap — TypeScript will error if they share a name.

```ts
const MyContext = contextFactory(
  { serve: "/docs/" as string | false },
  { paths: { sourceDir: "./src", testDir: ["sourceDir", "__tests__"] } },
);
// ctx.options.serve     → string | false (default applied)
// ctx.options.sourceDir → string | undefined (path override)
// ctx.resolve("testDir") → "<root>/src/__tests__"
```

### Auto-managed vs default files

- **Auto-managed** (`writeAutoGeneratedFile`): always overwritten by the tool; humans should not edit them; a `.bak` is created if a manual edit is detected.
- **Default** (`writeDefaultFile`): written once; users are free to edit; will not be overwritten.

### Entry point discovery

`resolveEntries(dir, filter)` (from `@mrmt/utils/fs`) walks a directory and returns a Rollup entry map. `filter` is a `RegExp` or `(path: string) => boolean`.

### Comment type detection

`resolveCommentType(filePath)` auto-detects `//`, `#`, or `<!-- -->` based on file extension. New types can be registered with `registerCommentTypeResolver()` (public via `@mrmt/vite/codegen`).

### Package name/version injection

`vp pack` replaces `import.meta.env.VITE_PACKAGE_NAME`, `import.meta.env.VITE_PACKAGE_VERSION` and `__MARMOTTE_VERSION__` with the **package's own** name/version at build time (see `tooling/pack.ts`). So a generated-file header names the package whose code wrote it. Packages are versioned in lockstep.

## Build system (Vite+)

- Each buildable package has a `vite.config.ts` calling `packageConfig(import.meta.dirname, { pack: { entry: {...} }, test: true })` from `tooling/pack.ts`. It returns the `pack` block (ESM, bundled per entry, `.js`/`.d.ts`, hidden sourcemaps) and the `build` / `test` tasks.
- **Task ordering comes from the dependency graph.** Workspace dependencies use the `workspace:^` protocol (that's what lets `vp run -r` and `--filter '<pkg>...'` order builds). `build` and `test` are tasks in the config, not `package.json` scripts (a task can't be defined in both); `test` also builds the package's `dependencies` and `devDependencies`.
- **API docs are generated during `build`** by the TypeDoc plugin (`@mrmt/unplugin-typedoc`, rolldown flavour) set up in `packageConfig`, into `packages/<pkg>/docs/api/` (gitignored). `@mrmt/utils` and `@mrmt/unplugin-typedoc` opt out with `api: false`: the plugin depends on `utils`, so documenting them with it would make the build graph cyclic. Every other package lists `@mrmt/unplugin-typedoc` as a `workspace:^` devDependency so `vp` builds it first. The plugin is imported lazily (`lazyTypeDoc` in `tooling/pack.ts`) because configs are evaluated before anything is built.
- A package that imports another one (or extends `@mrmt/tsconfig`) **must declare it** (`"@mrmt/x": "workspace:^"`): pnpm's `node_modules` is strict, nothing is hoisted by accident.
- `pnpm pack` / `vp pm pack -r` rewrite `workspace:^` to real ranges in the tarballs; never use `npm pack` here.

### Private packages are inlined

`@mrmt/utils` is `private`: consumers list it under **devDependencies** and tsdown bundles (and tree-shakes) what they import, types included. Consequences:

- A private package's own runtime dependencies must be declared by every consumer that inlines it (`@mrmt/vite` lists `zod` for the inlined `package-json` schema).
- Modules with global state (the comment-type registry in `codegen`) must be inlined by **one** package only, otherwise each package gets its own copy of the registry. Today only `@mrmt/vite` uses `codegen`; if another package needs it, re-export it from `@mrmt/vite` instead (`@mrmt/vite/codegen` does this for the public part).
- Don't import from `@mrmt/utils` in files that run outside a build of the consumer (it isn't installed for end users).

## Adding a new entry point to a package

1. Create the source file in `packages/<pkg>/src/`.
2. Add it to `pack.entry` in `packages/<pkg>/vite.config.ts`.
3. Add the matching `exports` key in `packages/<pkg>/package.json`.
4. `vp run @mrmt/<pkg>#build` to verify (check the `dist/` path matches the export).

## Adding a new package

1. Create `packages/<name>/` with `package.json` (`name`, `version` equal to the others, `type: "module"`, `workspace:^` for `@mrmt/*` deps incl. a devDependency on `@mrmt/tsconfig`, `files: ["dist", "!dist/**/*.map"]`, explicit `exports`, `publishConfig.access: "public"` for scoped names), `tsconfig.json` extending `@mrmt/tsconfig/tsconfig.node-lib.json`, and `vite.config.ts` using `packageConfig`.
2. It is picked up by `packages/*` in `pnpm-workspace.yaml`; add its `<name>#build` to the `api-docs` task's `dependsOn` in the root `vite.config.ts` (and `@mrmt/unplugin-typedoc` as a devDependency unless it opts out with `api: false`).
3. `vp install`, then `vp run build`.

## Adding a new Vite plugin

1. Create `packages/vite/src/<name>.ts` and export a `function MyPlugin(options): Plugin | Plugin[]` (Vue/Vuetify plugins go in `@mrmt/vite-ui`).
2. Use `DefaultVitePluginContext` for path resolution if needed.
3. Add the entry to `pack.entry` and the `exports` key (see above).
4. Write `packages/vite/src/<name>.test.ts`.

## Scripts (run from the repo root)

| Command              | Description                                                       |
| -------------------- | ----------------------------------------------------------------- |
| `vp run build`       | `vp run -r build`: every package in dependency order (cached)     |
| `vp run test`        | `vp run -r test`: unit tests + CLI scaffold integration tests     |
| `vp run check`       | `vp check`: oxfmt + oxlint (no type-check: use `tsc --noEmit -p`) |
| `vp run fmt`         | `vp fmt`                                                          |
| `vp run <pkg>#build` | one package, e.g. `@mrmt/vite#build`, `marmotte#test`             |
| `vp run docs`        | VitePress dev server (generates the API reference first)          |
| `vp run build:docs`  | API reference (TypeDoc) + VitePress site build                    |

## Testing

Unit tests live next to their source (`*.test.ts`). The scaffold integration tests are in `packages/cli/tests/`: they `vp pm pack` every publishable workspace package (not the private root or `@mrmt/utils`) and install **all** the tarballs together in generated projects (unpublished `@mrmt/*` dependencies can't come from the registry). Use `withTmpDir()` from `@mrmt/vitest` in hooks:

```ts
import { withTmpDir } from "@mrmt/vitest";
const { dir } = withTmpDir();
```

## Toolchain

- **Toolchain**: Vite+ (`vite-plus`) on pnpm (pinned via `devEngines`, downloaded by `vp`): `vp pack` (tsdown/rolldown), `vp test` (Vitest), `vp check`/`lint`/`fmt` (oxlint/oxfmt), `vp run` (cached tasks), `vp staged` + `.vite-hooks` (replaces husky + lint-staged)
- **Output**: ESM only, bundled per entry (so inlined code is tree-shaken), hidden sourcemaps (excluded from tarballs)
- **Types**: `dts: true` in `vp pack`; run `tsc --noEmit -p packages/<name>/tsconfig.json` for a full type-check including tests
- **Docs**: VitePress + TypeDoc. Each package generates its own API reference into `packages/<pkg>/docs/api/` (gitignored) as part of `build`; the site currently copies them in (`copy-api-docs.ts`). Direction: docs live next to their code (handwritten + generated per package) and the site aggregates them
- **Package schema**: Zod (`ZPackageJson` in `packages/utils/src/package-json.ts`)
